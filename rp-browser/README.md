# Researcher Profile Browser & Conformance Validator

A serverless single-page application with two functions:

1. Browser: ingest profile list documents or collection bundles, resolve
   manifests, browse / filter / cluster / search profiles from many origins.
   Free-text search runs entirely client-side (transformers.js loads
   all-MiniLM-L6-v2 in the page, no server needed).

2. Validator: paste a URL, fetch it from the browser, and report what is
   broken. CORS is the number-one practical blocker and it fails invisibly to
   the publisher; this tool catches it.

## Quick start

```bash
cd rp-browser
npm install
npm run dev          # Vite dev server on http://localhost:5185
```

To test against locally-published profiles, run `rp render` and `rp site`
first, then serve the output directory and add it as a source in the explorer.

## Search capability tiers

Not every source supports every feature. The explorer resolves a capability
tier per comparison group (profiles sharing the same `backend_spec`):

| Tier | Condition | Features |
|------|-----------|----------|
| 1 (local) | `st:all-MiniLM-L6-v2` + probe verified | Full free-text search in the page |
| 2 (vector-only) | Embeddings present, different backend or probe not yet run | "Similar to this profile", clusters, topics |
| 3 (no embeddings) | No embedding data | Inventory, filter, sort, substring search |

A published profile without a probe in its `embeddings/index.json` is not
Searchable (tier 1). The probe is a fixed sentence embedded by the publisher;
the explorer verifies local model compatibility by cosine-comparing its own
embedding against the publisher's vector (>0.99 = verified, 0.9-0.99 =
degraded, <0.9 = incompatible).

When multiple groups exist and the query is free-text, results render as
separate labeled sections; scores are never merged across groups.

## Self-hosted model

The ~23 MB quantized ONNX model is self-hosted under `public/models/` so the
app has no third-party runtime dependency and works offline. After a fresh
clone:

```bash
npm run fetch:model  # downloads model files into public/models/ (gitignored)
```

ONNX runtime WASM files are copied to `public/ort/` during the build by
`vite-plugin-static-copy`. This happens automatically; there is no manual step.

Set `VITE_RP_ALLOW_REMOTE_MODELS=1` to pull from the Hub instead.
`VITE_RP_APP_NAME` sets the title shown in the page shell (default
"Researcher Profile Browser"). The model
load path is lazy and failure-tolerant: the app builds and runs without any
model present in `public/models/`; search is unavailable until the model
loads.

## Document validation

The validator checks documents against JSON Schemas generated by rp-sdk and
committed in `rp-sdk/schemas/`, imported through the `@rp/schemas` alias,
using ajv (`src/validate/schemaValidation.ts`). Six schemas are loaded:

- `profile_jsonld`: the profile record and manifest (`profile.jsonld`)
- `papers_jsonld`: the works collection (`sources/papers.jsonld`)
- `embedding_index`: per-profile embedding index (`embeddings/index.json`)
- `profile_list`: profile list documents (JSON array of URLs)
- `collection`: collection bundles (`collection.jsonld`)
- `topic_index`: topic index (`collection/topics.json`)

`src/validate/profileChecks.ts` runs the first three on a profile (the
manifest, the `works` document it names, and the embedding index) and then
adds hand-written checks for what a schema cannot express: the ORCID
round-trip, the centroid dimension cross-check, and the format IRI gate.

## Skills tab

The Skills page links to the agent skills in
`rp-sdk/src/researcher_profiles/skill/` and `rp-sdk/skills/`.
`scripts/copy-skills.mjs` copies their markdown into `public/skills/`
(gitignored) so the built site serves the raw files; it runs automatically
before `dev` and `build`, or standalone via `npm run gen:skills`. Pass
`--out <dir>` to write them somewhere else.

## Embedding this app

This app is complete on its own: served from any static host it browses,
validates, and explains published researcher profiles, with no server behind it
and no account anywhere in the bundle.

A host application can also mount it and wrap it in its own chrome. Two
exports make that possible, and they are the whole contract:

```ts
import { mountApp } from "./mount";
import { ShellSlotsProvider } from "./shell/slots";

mountApp(document.getElementById("root")!, {
  routes: myRoutes,                       // mounted inside the shell layout
  wrap: (children) => (                   // your providers go here
    <MyProvider>
      <ShellSlotsProvider value={mySlots}>{children}</ShellSlotsProvider>
    </MyProvider>
  ),
});
```

`src/shell/slots.tsx` declares the six slots. Every one is empty by default,
and empty is the standalone app:

| Slot | What it adds or replaces |
|---|---|
| `navExtras` | Extra links appended to the top nav. |
| `headerRight` | The right-hand header cluster (identity, sign in, sign out). |
| `emptyScreen` | The zero-profile screen in Browse and the analysis views. |
| `homeActions` | The landing page's calls to action. |
| `aboutNote` | A paragraph on the About page describing how this deployment is served. |
| `profileTabs` | Extra tabs on a profile page, each with its own `enabled` predicate. |

`pageOf(pathname)` in `src/router.ts` returns `null` for any path this app does
not serve, including a host's own routes, so mounting under a host never lights
up the wrong nav link. Host routes are matched before the unknown-path
catch-all.

## Profile shape

A published profile is a single `schema:Person` document
(`profile.jsonld`) that is authored and published identically. Its file manifest
is the `hasPart` + `subjectOf` arrays of typed entries (PartRefs, keyed by
`role` with a relative `contentUrl`). The authoritative shape is
`rp-sdk/schemas/profile_jsonld.schema.json`; the explorer reads it in
`src/model/manifest.ts`.

## Build

```bash
npm run build        # tsc + vite build -> dist/
npm run preview      # serve the production build locally
npm run typecheck    # tsc --noEmit
npm run test         # vitest run
npm run test:watch   # vitest in watch mode
```

The build uses `base: "/"` and react-router's history router, so a static host
must serve `index.html` for unmatched paths (single-page-application fallback,
which `wrangler.toml` already configures). A sub-path deployment sets the base
at build time, for example `vite build --base=/explorer/`; the router basename
follows `import.meta.env.BASE_URL`.

## Deployment

A `wrangler.toml` is included for Cloudflare Workers Static Assets: it serves
`dist/` with no Worker script and single-page-application fallback.
